# 숫자 파싱 규칙 정리 및 음수 입력 방어 계획

## 목표

- 숫자 입력 처리 규칙을 화면별로 일관되게 맞춤
- UI 계층과 서비스 계층의 책임을 분리
- 음수 입력이 저장 시 양수로 보정되지 않도록 차단
- 빈 값은 UX에 맞게 `0` 또는 `null`로 일관 처리

## 문제 정의

현재 숫자 입력 처리에는 두 가지 문제가 있다.

- 화면에 따라 입력 중 숫자 처리 방식이 다름
- `parseNumber`가 음수 문자열을 양수로 보정할 수 있어 의미가 왜곡됨

이 상태에서는 같은 숫자 입력이어도 화면별 동작이 달라지고,
잘못된 입력이 저장 직전 조용히 다른 값으로 바뀔 수 있다.

## 변경 원칙

- UI 계층은 문자열 포매팅만 담당
- 숫자 변환과 저장 가능 여부 판단은 서비스 계층에서 담당
- 계산용 로직과 저장용 로직의 실패 처리 방식을 분리
- 음수 입력은 저장 시 실패로 처리
- 빈 값은 화면 UX를 해치지 않도록 `0` 또는 `null` 정책을 명시

## 목표 동작

### 숫자 파서 규칙

- `1,234` 같은 포맷 문자열은 `1234`로 변환
- 빈 문자열, 공백 문자열, `nullish` 값은 `0`으로 변환
- 음수 문자열과 음수 숫자는 `null`로 반환
- 숫자가 아닌 문자열은 `null`로 반환

### 계층별 책임

| 계층 | 역할 |
|---|---|
| UI | 입력 문자열 포매팅, 입력 상태 유지 |
| Hook | mutation 연결, 캐시 무효화 |
| Service | 숫자 파싱, 변경점 계산, 유효성 판단 |
| Repository | DB 컬럼 매핑 및 저장 |

### 저장 시 처리 규칙

| 입력 값 | 배분 저장 | 자산 금액 저장 |
|---|---|---|
| 양수 | 저장 | 저장 |
| 빈 값 | `0`으로 해석 후 저장 대상에서 제외 | `null`로 저장 |
| 음수 | 에러 처리 | 에러 처리 |
| 숫자가 아닌 문자열 | 에러 처리 | 에러 처리 |

## 구현 범위

### 1. 포트폴리오 숫자 변환 책임 이동

- `PortfolioList`에서 숫자 파싱 제거
- 입력 상태는 문자열 그대로 유지
- 자산 금액 변경점 계산은 서비스 계층으로 이동

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `components/dashboard/PortfolioList.tsx` | 입력 중 문자열 포매팅만 유지 |
| `hooks/useUpdateAssets.ts` | 서비스 호출 구조로 정리 |
| `services/asset/asset.service.ts` | 자산 금액 파싱 및 업데이트 payload 생성 |

### 2. 공통 숫자 파서 규칙 정리

- `parseNumber` 반환 타입을 `number | null`로 변경
- 음수, 비정상 문자열 감지 규칙 추가
- 빈 값은 `0`으로 반환하도록 정리

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `utils/formatters/parseNumber.ts` | 파싱 계약 변경 |

### 3. 저장 서비스 유효성 처리 추가

- 저장 서비스에서 `parseNumber` 결과가 `null`이면 예외 처리
- 배분 저장은 `0` 이하 항목을 저장 대상에서 제외
- 자산 금액 저장은 빈 값만 `null` 저장으로 허용

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `services/allocation/allocation.service.ts` | 배분 금액 검증 추가 |
| `services/asset/asset.service.ts` | 자산 금액 검증 추가 |

### 4. 계산용 훅 안전 처리

- 편집 중 합계 계산 로직은 `parseNumber(...) ?? 0` 사용
- 저장 검증 실패가 화면 계산을 깨지 않도록 방어

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `hooks/useAllocationHistory.ts` | 계산용 fallback 처리 |

### 5. 테스트 추가

- 숫자 파서 규칙 테스트 추가
- 배분 저장 음수 방어 테스트 추가
- 자산 금액 저장 음수 방어 테스트 추가

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `utils/formatters/parseNumber.test.ts` | 파서 케이스 검증 |
| `services/allocation/allocation.service.test.ts` | 배분 저장 검증 |
| `services/asset/asset.service.test.ts` | 자산 저장 검증 |

## 권장 진행 순서

`Step 1 -> Step 2 -> Step 3 -> Step 4 -> Step 5`

- 먼저 포트폴리오 입력 구조를 서비스 중심으로 정리
- 그 다음 공통 파서 규칙을 바꾸고
- 저장 서비스와 계산 훅을 각각 새 계약에 맞춤
- 마지막에 테스트로 정책을 고정

## 리스크

- `parseNumber` 계약 변경은 호출부 전반에 영향이 있음
- 빈 값을 `0`으로 볼지, 오류로 볼지 화면별 UX 차이가 있음
- 저장 경로와 계산 경로가 같은 파서를 쓰므로 역할 분리가 불명확하면 후속 변경이 어려워질 수 있음

## 확인 포인트

- `allocation` 화면에서 빈 금액 항목이 있어도 저장 흐름이 깨지지 않는지 확인
- `history` 편집 중 빈 값과 음수 값이 합계 계산을 깨지 않는지 확인
- `portfolio` 수정에서 빈 값은 `null`, 음수는 오류로 구분되는지 확인
- 서비스에서 던진 검증 오류가 mutation 경로를 통해 UI까지 전달되는지 확인
