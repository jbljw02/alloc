# 내역 페이지 월별 자금 흐름 수정 기능 도입 계획

## 개요

현재 `내역 페이지`에서는 월별 자금 흐름 조회만 가능하고,
실제 입력은 `배분 페이지`에서 이번 달 데이터만 신규 저장할 수 있다.

이 문서는 `내역 페이지`에서 선택한 월의 자금 흐름을 직접 수정할 수 있도록 기능을 확장하는 단계별 계획을 정리한다.

---

## 현재 상태

| 영역 | 현재 동작 | 한계 |
|---|---|---|
| `app/(tabs)/history.tsx` | 월별 자금 흐름 조회 | 읽기 전용 |
| `app/(tabs)/allocation.tsx` | 이번 달 배분 입력 및 저장 | 과거 월 편집 불가 |
| `services/allocation/allocation.service.ts` | 저장 시 항상 현재 날짜 기준 `allocationMonth` 사용 | 선택한 월 저장 불가 |
| `allocationRepository.bulkCreateAllocation()` | 저장 시 신규 row만 추가 | 수정/삭제 불가 |
| `assetRepository.bulkUpdateBalance()` | 저장 금액을 자산 잔액에 누적 반영 | 과거 월 수정 시 중복 누적 위험 |

---

## 문제 정의

현재 저장 구조는 사실상 `추가`만 지원한다.

- 같은 월 데이터를 다시 저장해도 기존 데이터를 대체하지 않고 신규 row를 추가한다.
- 자산 잔액도 입력 금액만큼 다시 누적된다.
- 따라서 `내역 페이지`에서 월별 데이터를 수정하려면 단순 UI 변경이 아니라 저장 방식 자체가 `추가/수정/삭제`를 모두 처리하도록 바뀌어야 한다.

---

## 목표

- `내역 페이지`에서 선택한 월의 배분 데이터를 편집할 수 있어야 한다.
- 저장 시 선택한 월 기준으로 동작해야 한다.
- 기존 월 데이터와 비교하여 `추가/수정/삭제`를 구분 처리해야 한다.
- 자산 잔액은 변경 전후 차이만 반영되어야 한다.

---

## 단계별 작업

### Step 1: 내역 페이지 편집 모드 UI 도입

- `history` 화면에서 선택한 월 데이터를 편집 가능한 상태로 전환
- 기존 `HistoryItemList`를 읽기 전용/편집 모드 둘 다 지원하도록 확장하거나 편집 전용 리스트 분리
- 지원 기능
  - 금액 수정
  - 항목 제거
  - 자산 추가
  - 편집 취소
- 이 단계에서는 저장 로직을 바로 완성하지 않고 UX와 상태 구조를 먼저 정리

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `app/(tabs)/history.tsx` | 편집 모드 진입/종료 UI 추가 |
| `components/history/HistoryItemList.tsx` | 읽기 전용/편집 UI 확장 |
| 필요 시 `components/allocation/AllocationList.tsx` | 공통 리스트 재사용 구조 검토 |
| `hooks/useAllocationHistory.ts` | 편집용 상태 관리 추가 |

---

### Step 2: 저장 기준 월을 선택 월로 확장

- 저장 훅과 서비스가 `선택한 월`을 입력받도록 변경
- 기존 `new Date()` 고정 로직 제거
- `history` 화면에서 현재 선택한 월 정보를 저장 로직에 전달

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `hooks/useSaveAllocation.ts` | mutation 인자 확장 |
| `services/allocation/allocation.service.ts` | 저장 월 파라미터 처리 |
| `app/(tabs)/history.tsx` | 선택 월 전달 |

---

### Step 3: 월 단위 동기화 로직 도입

- 저장 시 선택 월의 기존 배분 데이터와 현재 편집 데이터를 비교
- 항목별로 아래 동작 수행
  - 신규 항목: 생성
  - 기존 항목 + 금액 변경: 수정
  - 기존 항목 + 제거됨: 삭제
- 이 단계에서 `insert only` 구조를 `sync` 구조로 전환

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `services/allocation/allocation.service.ts` | 비교 및 동기화 로직 추가 |
| `repositories/allocation.repository.ts` | 월별 조회, 수정, 삭제 조합 지원 |
| `types/domain/allocation.ts` | 필요 시 편집 흐름용 식별 정보 재검토 |

---

### Step 4: 자산 잔액 보정 로직 적용

- 기존 방식은 입력값 전체를 잔액에 누적
- 수정 기능에서는 기존 값과 새 값의 차이(`diff`)만 반영해야 정합성 유지 가능
- 삭제는 음수 diff, 수정은 증감 diff, 신규는 양수 diff 반영

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `services/allocation/allocation.service.ts` | diff 계산 로직 추가 |
| `repositories/asset.repository.ts` | 기존 RPC 재사용 또는 입력 형식 조정 |

---

### Step 5: 예외 처리 및 UX 마감

- 빈 데이터 저장 방지
- `0원` 입력 처리 기준 통일
- 해당 월 데이터가 없을 때 편집 시작 UX 정리
- 저장 성공/실패 메시지 정리
- 현재 월/과거 월 편집 플로우 점검

#### 예상 변경 파일

| 파일 | 작업 |
|---|---|
| `app/(tabs)/history.tsx` | Alert, 버튼 상태, 안내 문구 정리 |
| `components/history/HistoryItemList.tsx` | 빈 상태 및 입력 UX 정리 |
| `services/allocation/allocation.service.ts` | 유효성 처리 보강 |

---

## 권장 진행 순서

`Step 1 -> Step 2 -> Step 3 -> Step 4 -> Step 5`

- 가장 먼저 화면 편집 구조를 안정화하고
- 그 다음 저장 기준 월을 일반화한 뒤
- 마지막에 데이터 정합성 로직을 붙이는 순서가 가장 안전하다

---

## 영향 범위

| 구분 | 영향 |
|---|---|
| UI | 내역 페이지에 편집 진입/저장/취소 흐름 추가 |
| 데이터 저장 | 현재 월 고정 저장에서 선택 월 저장으로 확장 |
| DB 반영 방식 | 단순 insert에서 월 단위 sync로 전환 |
| 자산 잔액 | 누적 방식에서 diff 반영 방식으로 보정 필요 |

---

## 주의사항

- 이 작업은 화면 수정만으로 끝나지 않고 데이터 정합성 변경이 포함된다.
- 특히 과거 월 수정 기능은 자산 잔액 계산 방식과 직접 연결되므로 `Step 3`, `Step 4`를 분리해서 검증해야 한다.
- 사용자 변경 사항이 있는 워크트리가 있으므로 관련 없는 파일은 건드리지 않고 최소 범위만 수정해야 한다.

---

## 이번 작업의 시작점

가장 안전한 첫 작업은 `Step 1: 내역 페이지 편집 모드 UI 도입`이다.

이 단계에서는 실제 DB 동기화까지 한 번에 처리하지 않고,
`내역 페이지에서 수정 가능한 UX와 상태 구조를 먼저 완성`하는 것을 목표로 한다.
